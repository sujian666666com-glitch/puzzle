# delegate-cli 动态需求与任务蓝图

## 交互改造需求与实施建议

- 整理日期：2026-11-03
- 适用对象：用户提供的 `delegate-cli` Skill 及其配套面板
- 文档状态：需求定义与方案建议，尚未实施
- 调研依据：本次提供的源码、Claude Code 官方文档及官方 Mods 类型定义

> 在保持现有开发与验收流程的基础上，增加一份随执行持续更新的需求与任务蓝图。蓝图统一表达需求、任务关系、Agent 分工、运行状态和验收结果，并根据 Claude Code 当前界面的能力，以文字、任务树、列表、卡片、关系图或 HTML 等方式呈现。

## 1. 改造目标

用户需要先看懂“准备做什么”，执行时能持续知道“谁在做、做到哪里、等待什么”，完成后能够找到结果和验收证据。

“拼图”表达需求的整体、组成与关联。每一块对应有意义的需求单元；多个块共同组成完整目标。拼图轮廓、卡片样式和 hover glow 都属于可选的视觉表达，不应限制需求模型和输出载体。

本次改造的核心要求：

1. **多种呈现形式。** 根据任务特点、复杂度和当前界面能力，选择文字、分组清单、任务树、卡片、依赖图或网页。
2. **同一份内容与状态。** 各种视图共享需求、任务和执行记录，切换呈现形式后保持一致。
3. **执行过程可见。** 需求块持续展示对应 Agent、当前阶段、最新活动、依赖和阻塞。
4. **按需展开细节。** 支持的界面通过悬停显示摘要，通过点击查看完整说明、运行记录和结果；其他界面提供等价的信息入口。
5. **保留现有执行闭环。** 委派、隔离、并发、续接、审查、权限和主控验收继续遵循现有规则。

## 2. 用户流程

**用户提出任务 → Claude 理解需求 → 需求具体说明 → 生成需求蓝图 → 原有任务分配与执行 → 原有验收与交付。**

蓝图在执行开始前形成，并在后续过程中持续更新。

| 阶段 | 蓝图呈现内容 | 更新时机 |
| --- | --- | --- |
| 理解需求 | 目标、范围、约束、待澄清项 | Claude 完成需求归纳后 |
| 具体说明 | 各需求单元、行为规则、完成标准 | 需求说明形成或修订时 |
| 任务分配 | 子任务、负责 Agent、角色、前置依赖 | 派发任务前后 |
| 实际执行 | 当前动作、执行状态、耗时、阻塞原因 | 运行记录更新时 |
| 审查与验收 | 审查意见、验证结果、未通过项 | 审查或验证完成时 |
| 交付 | 已通过条件、最终结果、产物入口 | 主控完成验收后 |

延续用户已有授权，不新增逐块确认或强制审批。只有缺失信息确实阻碍继续工作时，才向用户提问。

## 3. 蓝图的组织方式

### 3.1 需求块、任务与运行记录

需要明确区分三个身份：

**需求块 → 一个或多个任务 → 每个任务的一次或多次 Agent 运行。**

Claude Code 原生任务清单和后台任务视图分别表达规划与实际运行，本方案通过稳定的关联关系连接这两层。[^9]

| 对象 | 表达什么 | 最小内容 |
| --- | --- | --- |
| 需求块 | 用户希望实现的能力或结果 | 稳定 ID、名称、说明、范围、验收条件、关联任务 |
| 任务 | 为实现需求需要完成的具体工作 | 稳定 ID、关联需求、角色、负责人、依赖、任务状态 |
| 运行 | 某个 Agent 的一次实际执行 | 运行 ID、Agent、模型、会话、状态、时间、活动、结果位置 |
| 验收记录 | 是否满足完成条件 | 对应条件、通过情况、证据、主控结论 |

一个需求块可以包含实现、代码审查、浏览器验收等任务。一个共享任务也可以服务于多个需求块。

续接、重试或更换 Agent 时，保留原需求块和任务身份，新增运行记录。会话 ID 用于续接，不能代替需求块 ID。

### 3.2 示例

以下为结构示例，不代表实际运行数据。

| 需求块 | 任务 | 执行记录 |
| --- | --- | --- |
| 商品搜索 | 实现搜索接口 | Codex 首次实现、后续修复 |
| 商品搜索 | 审查搜索逻辑 | Cursor 审查 |
| 商品搜索 | 验收搜索用户流程 | Codex 界面验收、Claude 收回检查 |

无论查看文字、列表还是图形，这些记录都属于同一个“商品搜索”需求块。

### 3.3 关系表达

至少区分以下关系：

- **包含关系**：某需求由哪些子需求或任务组成。
- **依赖关系**：某任务开始前，需要哪个任务满足什么条件。
- **参与关系**：哪些 Agent 参与实现、审查或验收。
- **结果关系**：某次执行交付了什么，哪些证据支持验收结论。

空间相邻、拼接轮廓或同色分组仅用于辅助阅读。执行依赖必须来自明确的任务关系，不能由视觉位置推断。

## 4. 呈现方式与选择规则

### 4.1 按任务选择形式

| 任务特点 | 建议呈现 |
| --- | --- |
| 规模小、路径清楚 | 文字说明与简短状态清单 |
| 有明显层级和子任务 | 需求树或分组列表 |
| 多个 Agent 并行工作 | 卡片或任务列表，突出负责人和状态 |
| 前后依赖较多 | 关系图，突出等待对象和受影响任务 |
| 需要丰富视觉交互 | 支持该能力的原生视图，或网页增强视图 |
| 需要阶段汇报或分享 | Markdown 文档或 Artifact |

不要求每个任务都生成 HTML，也不要求所有界面复刻同一种视觉效果。所有形式都应能表达核心需求、负责人、状态、依赖和结果。

### 4.2 Claude Code 能力核对

以下是调研时的官方能力；实际落地需以目标客户端、版本和可用扩展接口核对。[^1][^2][^3]

| 载体 | 已核实能力 | 本方案的适配方式 |
| --- | --- | --- |
| 普通文字输出 | 可用文字组织需求与状态 | 保留完整的信息表达，通过编号或后续查询定位详情 |
| Terminal Mod | Pane、文字、布局块、按钮、键盘操作、hover 样式 | 以清晰的列表和需求块为主；鼠标交互结合终端渲染模式适配 |
| Desktop Mod | Pane、原生元素、hover 浮层、关联高亮、SVG、Client | 优先承载本机实时蓝图与 Agent 状态 |
| VS Code Mod | Pane、文字、按钮、输入和 SVG；当前忽略原生元素的 hover 属性，且不支持 Client | 通过点击或键盘展开相同信息 |
| Desktop Browser | 可打开本地 HTML 和运行中的网页 | 提供更丰富的交互；实时状态另行接入本地数据桥接 |
| Artifact | HTML/Markdown 页面、交互、同一 URL 重新发布更新 | 用于阶段展示和分享，采用明确的发布更新机制 |

Desktop 的本地网页预览能力见官方说明。[^5]

### 4.3 Hover 与视觉效果的边界

官方 Mods 类型定义已经提供悬停显示隐藏浮层、绝对定位和分组高亮能力。关联元素可以使用同一 hover 分组产生联动。[^4]

原生 hover 由界面直接处理，不会因鼠标经过就触发模型调用。悬浮信息应来自已经刷新到界面的状态数据。

hover glow 是视觉增强：终端可以采用边框、背景和文字强调；Desktop 可以选择原生元素或 SVG 等方式增强。浏览器式柔光、渐变和光斑跟随需要按目标界面验证。原生元素和 Client 不等同任意 HTML/CSS 容器。[^3][^4]

### 4.4 Artifact 的更新方式

Claude 可以修改文件并重新发布到同一个 Artifact URL，使打开的页面更新。但已发布页面不能直接调用本地 `.mcp.json` 服务，也不会自动读取本机运行文件；运行时 connector 能力仅覆盖声明的 claude.ai 连接。[^6]

本方案建议用原生 Mod 承担本机实时观察，用 Artifact 承担阶段更新与分享。若使用本地网页，应明确由本地数据服务提供状态。

## 5. 交互要求

### 5.1 全局视图

每个块至少显示名称、当前状态和负责人。界面空间允许时，补充当前阶段和验收进度。

用户能够快速判断：

- 哪些工作正在进行。
- 哪些工作等待前置任务。
- 哪些工作执行结束但还未验收。
- 哪些工作已通过验收。
- 哪些工作受阻，以及原因是什么。

### 5.2 悬停摘要

支持 hover 的界面，悬停时显示：

| 信息 | 要求 |
| --- | --- |
| Agent 与角色 | 显示当前执行者，并区分实现、审查、验收等职责 |
| 模型 | 有记录时显示真实模型；无法确认时不补造 |
| 当前状态 | 使用结构化状态和明确原因 |
| 最新活动 | 展示最近工具活动或明确的进度摘要 |
| 耗时与更新时间 | 帮助判断工作是否仍在推进、信息是否新鲜 |
| 依赖与阻塞 | 说明等待哪个任务或缺少什么条件 |
| 验收进度 | 有明确验收项时显示已通过数与总数 |

同一块由多个 Agent 参与时，显示角色集合或当前执行者与历史参与者，避免丢失审查和返工记录。

悬浮摘要保持简短；完整日志、长说明和证据放在点击详情中。

### 5.3 点击详情

点击后展开该块的：

- 需求描述、业务规则、范围与验收条件。
- 子任务、前置依赖、负责人和当前阶段。
- Agent 执行历史，包括续接和失败记录。
- 结果、日志和验证证据入口。
- 未解决问题及下一步。

展开局部详情时保留全局位置与返回路径。点击查看详情本身不应启动新的执行、重试、提交或部署。

### 5.4 关联与更新

悬停或选中某块时，可以突出其前置任务和下游任务。前置条件满足后更新等待状态，是否派发仍由原有主控流程决定。

需求被补充或修订时，更新同一需求记录及其受影响关系。已完成的执行证据保留；如果变更影响验收有效性，标明需要重新验证。

## 6. 状态与进度规则

### 6.1 执行状态与业务验收分别记录

当前 runner 的 `process_succeeded` 仅表示 CLI 执行及结果格式满足条件，`verified` 始终为 `false`。主控验收之后，业务任务才可以标为已完成。[^10]

| 当前运行信息 | 蓝图建议显示 |
| --- | --- |
| `planned` | 仅生成执行计划，尚未运行 |
| `preparing` | 准备执行 |
| `running` | 执行中，并附当前活动 |
| `process_succeeded` | 执行结束，待验收 |
| `blocked` | 运行条件受阻，并说明原因 |
| `failed` / `timed_out` / `cancelled` | 失败 / 超时 / 已取消 |
| 主控确认验收通过 | 已验收 |
| 主控确认仍有问题 | 需要修复或补充验证 |

“等待前置任务”属于任务关系状态，与模型、目录信任、锁冲突等导致的运行受阻分别说明。

### 6.2 进度的依据

优先展示三类信息：

1. **阶段**：实现、测试、审查、验收。
2. **当前活动**：例如正在执行回归测试。
3. **可核验数量**：例如验收条件 2/4 项通过。

耗时、token、工具调用次数和心跳用于观察运行，不直接换算为业务完成百分比。官方 SDK 的任务进度事件也没有通用业务完成百分比字段。[^8]

如采用百分比，必须标明计算口径，例如“验收项通过比例”；它不代表剩余工期。没有可靠分母时保留阶段和活动，不生成假精度。

### 6.3 数据新鲜度

显示最近更新时间。心跳或数据长时间未更新时标为“状态待核实”，保留最后已知状态，核实进程后再作判断。

当前面板已经会对长时间无进度的运行提示“可能已中断”；该提示不等于已确认失败。[^10]

## 7. 最小实施方案

### 7.1 现有基础

当前 Skill 已保存 Agent、模型、会话、状态、时间、用量、错误、进度与结果；面板已支持运行卡片、定时刷新和点击查看详情。[^10]

主要缺口是需求块、任务、依赖、验收与这些运行记录之间的结构化关联。

### 7.2 职责划分

| 部分 | 职责 |
| --- | --- |
| Claude 主控 | 理解需求、生成说明、拆分任务、维护依赖与分工、作出验收结论 |
| 现有 runner | 按原规则执行 CLI，记录真实运行状态、会话、日志和结果 |
| 新增关联与汇总逻辑 | 将需求、任务、运行记录和验收结果连接起来，生成一致状态 |
| 各种视图 | 展示相同内容，处理选中、悬停、展开和界面适配 |

通过 Bash 启动的 Codex/Pi/Cursor 应继续使用 runner 记录作为状态源。Claude 原生子 Agent hooks 有特定触发范围，不会自动识别这些外部 CLI 为原生子 Agent。[^7]

### 7.3 建议改动位置

| 位置 | 第一版建议改动 |
| --- | --- |
| `SKILL.md` | 增加需求理解、具体说明、蓝图生成和状态维护约定；后续交接引用稳定的需求与任务 ID |
| 独立蓝图状态 | 保存需求块、任务依赖、分工、验收条件及结论 |
| 任务与运行的关联 | 先用旁侧映射绑定任务与现有 `run_file`，保留每次执行历史 |
| `panel/types/index.d.ts` | 增加需求、任务、依赖、验收和运行关联的数据结构 |
| `panel/hooks/register.tsx` | 在已有运行详情之上增加需求/任务视图及界面适配 |
| `scripts/run_cli.py` | 第一版优先复用既有行为；确需扩展时，仅增加可选的关联元数据 |

启动前校验失败也应归属到对应任务，即使 runner 尚未创建运行目录，仍记录派发失败及原因。

业务验收状态建议独立维护。现有面板缓存已经结束的运行；仅修改终态 `run.json`，不能保证面板及时反映新的验收结论。[^10]

### 7.4 更新机制

执行时复用运行记录的增量读取和现有刷新机制；需求变更、任务分配和主控验收发生时更新蓝图状态。Hover 和点击读取已汇总的数据，不为每次交互重新调用模型。

首次打开或恢复会话时，从持久化蓝图和运行记录重建视图。加载中、缺失、过期和已确认完成等状态应可区分。

## 8. 第一版范围

第一版优先交付：

1. 一份共享的需求、任务与运行关联数据。
2. 可独立使用的文字/清单表达。
3. 基于现有面板的需求/任务视图。
4. Agent、活动、依赖、阻塞和验收状态展示。
5. Terminal/Desktop 的原生 hover 摘要，以及各界面的点击或键盘详情入口。
6. 续接和恢复后仍可追踪的执行历史。

后续按需要增加复杂关系图、丰富 glow 效果、本地网页和 Artifact 输出。具体视觉强度根据目标界面实测结果决定。

## 9. 验收清单

以下为待实现的验收标准。

- [ ] Claude 先形成具体需求说明，再生成对应蓝图；蓝图能追溯到需求内容。
- [ ] 同一任务可用文字及至少一种交互形式呈现，内容和状态一致。
- [ ] 用户能直接识别正在执行、等待依赖、受阻、待验收和已验收的块。
- [ ] 悬停摘要展示真实 Agent、角色、状态及活动；不支持 hover 时可通过点击或键盘获取。
- [ ] 选中某块能查看其依赖和受影响任务，关系与任务定义一致。
- [ ] 一个需求经过多个 Agent、续接或重试后，仍能查看完整任务和运行历史。
- [ ] CLI 正常结束显示为待验收；主控验收通过后才显示业务完成。
- [ ] 进度具有明确依据，耗时、token 和心跳不会被当作完成百分比。
- [ ] 状态过期时显示更新时间或待核实提示，不自动虚构成功、失败或进展。
- [ ] 需求修订后，各视图同步更新，受影响的验收条件被标记为需要复验。
- [ ] 原有委派、权限、隔离、并发、续接和验收规则保持既定职责，不增加逐块审批。
- [ ] 会话恢复或面板重开后，可重建需求、任务、依赖、执行和验收状态。

## 10. 落地前核对项

这是兼容性检查，不是新增审批流程。

- 确认主要使用 Terminal、Desktop Code 还是 VS Code 扩展。
- 核对目标界面的 Claude Code/扩展版本和 Mod 是否可用。
- 使用目标安装版本生成的类型定义核对实际元素与属性。
- 在该界面实测悬停浮层、点击、键盘访问、状态刷新和恢复行为。
- 只有选择 Artifact 时，再核对账号可用性和发布更新路径。

官方文档给出的 Mods 基础版本包括 Terminal Claude Code 2.1.287+、Desktop 内置 Claude Code 2.1.286+；VS Code 渲染需要扩展 2.1.299+，不获取 feature flags 的相应会话需要 2.1.304+。具体元素仍应以目标安装版类型与实测为准。[^1][^2][^3]
